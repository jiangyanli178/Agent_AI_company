## 二、按量计费的口径（避免"乱扣钱"的质疑）

AI 类动作采用「**预扣封顶 + 按实结算 + 多退不补**」：

```
发问前   预扣 5 积分，页面显示"本轮最多 5 积分"
返回后   按真实 token 折算，例如应扣 2 积分
         自动退回 3 积分，流水留一条 REFUND
         页面显示"实扣 2 积分，已退回 3 积分"
```

**多退不补**：实际成本超过封顶时，不多收，由公司承担。

### 成本失控的防线（重要）

封顶**不能**兜住成本。极端情况：用户贴 20 万 token，成本约 0.56 元，
封顶只收 0.5 元，公司是亏的。

真正的防线在调模型之前：

| 参数 | 值 | 作用 |
|---|---|---|
| `MAX_INPUT_TOKENS` | 问答 8000 / 诊断 30000 / 优化 80000 | 超限提示用户分段 |
| `MAX_HISTORY_TURNS` | 6 | 只带最近 6 轮上下文，防止 token 线性膨胀 |
| `MARKUP` | 12 | 成本加价倍率，对应毛利约 92% |

## 四、现金流特点：预收前置

积分是**预付费**。卖 100 张 49 元标准包 = **4900 元现金当日入账**，
而对应的服务成本分摊在未来数月。

对一人公司而言，这意味着：
- 不需要垫付运营资金
- 现金流始终为正，不存在"先烧钱后赚钱"的阶段
- 未消耗积分形成沉淀，但**不构成收入**，财务上属于递延

**记账口径**：充值时记为"预收"，积分实际消耗时才确认为收入。
这样计算出的毛利才是真实的，不会把"用户充了但还没用"的部分算成利润。

## 五、每周对账 SQL（财务 Agent 用）

```sql
-- ① 本周营收
SELECT COUNT(*) AS orders,
       SUM(price_cny) AS gmv_cny,
       COUNT(DISTINCT user_id) AS paying_users
FROM recharge_orders
WHERE status='PAID' AND created_at > DATE_SUB(NOW(), INTERVAL 7 DAY);

-- ② 积分消耗结构：用户的钱花在哪
SELECT biz_type, COUNT(*) AS times, SUM(-amount) AS points
FROM credit_transactions
WHERE change_type='CONSUME'
  AND created_at > DATE_SUB(NOW(), INTERVAL 7 DAY)
GROUP BY biz_type ORDER BY points DESC;

-- ③ 真实 token 消耗（用于重算实际毛利）
SELECT SUM(tokens_in) AS tokens_in, SUM(tokens_out) AS tokens_out
FROM ai_messages
WHERE created_at > DATE_SUB(NOW(), INTERVAL 7 DAY);

-- ④ 预收沉淀（尚未消耗的部分，属于递延而非收入）
SELECT SUM(balance) AS outstanding_points,
       SUM(balance) * 0.10 AS outstanding_cny
FROM credit_accounts;

-- ⑤ 账目自查：余额必须等于流水求和
SELECT (SELECT SUM(balance) FROM credit_accounts) AS balance_sum,
       (SELECT SUM(amount)  FROM credit_transactions) AS tx_sum,
       (SELECT SUM(balance) FROM credit_accounts) =
       (SELECT SUM(amount)  FROM credit_transactions) AS consistent;
```

**第 ⑤ 条是隐藏加分项**：一个能自己对账的系统，答辩时几乎没有对手会展示。
