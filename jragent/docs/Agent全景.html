实现细节：为什么工具描述写得那么啰嗦

TOOLS 里每个工具的描述都是给模型看的判断依据，不是给人看的文档。 所以里面写满了「用户说『…』时调用」「不传这个参数会怎样」「绝对不要回答『我做不了』」。 描述越具体，模型选错工具的概率越低 —— 这是提示词工程里最划算的一处投入。

存储：一张普通的表

没有独立的向量库、没有 embedding 服务。就是 kb_documents 这张表：

id · category · title · content
keywords · related_strategy_code
sort_no · active · created_at

想加一篇？插一行就行，不用重建索引跑批处理。 related_strategy_code 让「什么是 RSI 超卖」能顺手链到策略库里的那条策略。

检索：全文索引 + LIKE 兜底

-- 主力：ngram 全文索引，按相关度排序
SELECT ... MATCH(title, content)
  AGAINST (:q IN NATURAL LANGUAGE MODE) AS score
FROM kb_documents
WHERE active=1 AND MATCH(title, content) AGAINST (:q ...)
ORDER BY score DESC LIMIT 3

-- 兜底：极短词/纯标点时全文索引会返回空
SELECT ... WHERE title LIKE :k
   OR content LIKE :k OR keywords LIKE :k

第二段不是多余的。中文两字词在 ngram 下偶尔会被切碎， 一旦全文索引返回 0 条，用户就会看到「我不知道」——兜底能救回这种情况。

另一个「知识源」别搞混：hub/ 9 卷宗

hub/00-charter.md 到 08-review.md 是公司决策档案： 宪章、市场、品牌、产品、运营、数据管道、财务、日志、复盘。 它是给人（和写代码的 AI）看的事实来源，规定「所有 Agent 的产出不得与宪章冲突」。

它不进检索，也不喂给对话模型 —— 那是公司治理文档，不是给用户解答「什么是夏普比率」用的。 两套东西：一个管怎么做事（hub），一个管怎么回答（kb_documents）。

06一次提问，9 步走完

以「这个策略靠不靠谱」为例，时间是真实观测值。

  1. 前端发起 SSE 请求 前端

    POST /api/ai/chat/stream，带上历史消息和附件（图片转 base64）。

  2. 预扣 5 积分 finance

    余额不够直接拦，不发请求、不清输入框，弹充值框。这一步保证不会白嫖算力。

  3. 拼上下文 support

    系统提示词 8,265 字（含 19 个工具的调用规则）+ 最近 6 轮（12 条）上下文 + 附件。
    输入超 8,000 token 先截断 —— 这是成本防线，比封顶更有效。

  4. 模型开始思考　约 1.6 秒 support

    流式返回 reasoning_content，前端立刻把思考过程画出来。 这就是「能看出它没卡」的地方。

  5. 模型要调工具　约 3 秒起 product

    比如 run_backtest：读 daily_bars 的真实日线，跑一遍含手续费的回测， 算出收益/回撤/夏普/胜率，再回灌给模型。最多循环 6 轮。

  6. 出正文 support

    模型用大白话解释数字，该说的坏消息照说（「三个策略都跑输了买入持有」）。

  7. 合规终审 risk

    禁词扫描 → 命中就打回重写（最多 3 轮）→ 通过后强制加免责尾注。 被改写时前端收到 replace，整段替换掉已显示的内容。

  8. 按真实用量结算 finance

    预扣 5 分 → 按 token 折算 → 多退少补（封顶 5 分）。 没答出正文就 全额退，连已扣的工具费也逐笔退。

  9. 推 done，前端刷新余额 support

    带上 charged / refunded / balance， 界面上显示「本次实扣 N 积分（已退回 M）」。

为什么要把「失败」也设计进去：模型空返回、网络断、思考吃光预算，这些都会发生。 现在的处理是「钱一定退、状态记 DEGRADED、给用户一句能看懂的话」—— 而不是扣了 5 分然后显示空白。
