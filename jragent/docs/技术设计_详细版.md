### 为什么不用这些

| 不选 | 原因 |
|---|---|
| LangChain / LlamaIndex | 抽象层太厚，调试一个 prompt 要翻三层源码；直接 httpx 调 API 只要 30 行 |
| backtrader / vnpy | 装包 + 学 API 要 4-6 小时，自写只要 1.5 小时，且能精确控制防未来函数 |
| 向量数据库 | 16 篇知识库文档用 MySQL ngram 全文检索足够，省 4 小时和一台服务器 |
| Element Plus / Ant Design Vue | 学习成本 + 体积 + 样式覆盖成本，超过自写一套的成本 |
| Redis | 40 小时内不需要缓存；余额读库一次 1ms，够用 |
| Docker | 现场部署多一层出错可能，直接 systemd 跑 uvicorn |

## 三、数据库设计

### 3.1 表清单（14 张 + 2 视图，已在 `schema.sql` 中可直接执行）

| # | 表 | 作用 | 关键约束 |
|---|---|---|---|
| 1 | `users` | 账号 | `uk_phone` |
| 2 | `credit_accounts` | 余额（唯一权威） | `CHECK balance >= 0` |
| 3 | `credit_transactions` | 流水，append-only | `uk_idem` 幂等键 |
| 4 | `credit_packs` | 充值档位 | `uk_code` |
| 5 | `recharge_orders` | 充值订单 | `uk_order_no` |
| 6 | `symbols` | 标的 | 主键 code |
| 7 | `daily_bars` | 日线 | `PK(symbol_code, trade_date)` |
| 8 | `strategies` | 策略库（官方 + 用户自建） | `uk_code` |
| 9 | `backtest_jobs` | 回测任务与结果 | `uk_job_no` |
| 10 | `deployments` | 模拟盘部署 | `idx_charge(status, last_charge_date)` |
| 11 | `signals` | 每日信号 | `uk_dep_date` 防重复 |

两个视图：`v_agent_kpi`（人事档案直接 SELECT）、`v_revenue_daily`（营收看板）。

### 3.2 三个关键设计决策

**① 余额只放一处，流水永不 UPDATE**

余额在 `credit_accounts.balance`，任何变更必须同时插一条 `credit_transactions`。
`credit_transactions` 只 INSERT，不做 UPDATE/DELETE。
这样任何时刻都能用 `SELECT SUM(amount)` 校验余额，出了问题能定位到具体哪一笔。

**② 回测结果整包存 `result_json`，不建曲线表**

一张 500 点的净值曲线，拆成表就是 500 行，读一次要 JOIN 再排序。
塞进 JSON 一次读完，前端直接 `JSON.parse` 喂给 ECharts。
MySQL 8 的 JSON 列没有明显性能问题，40 小时的场景下这个取舍完胜。

**③ `points_cost` 存进每一笔业务表**

`backtest_jobs.points_cost`、`ai_messages.points_cost` 都要落库。
这样答辩时一句 SQL 就能算出「某个功能实际消耗了多少积分 vs 收了多少积分」，单位经济不用手算。

### 3.3 索引要点

| 索引 | 为什么 |
|---|---|
| `daily_bars PK(symbol_code, trade_date)` | 回测按标的 + 区间范围扫描，聚簇索引天然有序 |
| `credit_transactions uk_idem` | 幂等，防重复扣费/重复入账 |
| `deployments idx_charge(status, last_charge_date)` | 定时任务扫「今天还没扣费的运行中部署」，走索引 |
| `signals uk_dep_date` | 同一部署同一天只出一条信号，定时任务跑两次不会脏数据 |
| `kb_documents FULLTEXT ngram` | 中文全文检索，不引入向量库 |
| `strategies idx_cat(category, is_public)` | 策略库按分类筛选，这是最高频查询 |

### 3.4 为什么用 SQLAlchemy Core 而不是 ORM

- 表结构以 `schema.sql` 为唯一真相，ORM 的模型定义会和 DDL 漂移，两边不一致是 hackathon 最常见的坑
- 积分扣费这种逻辑，写清楚 SQL 比写清楚 ORM 的 session 状态更容易 review
- Core 一样能防 SQL 注入（参数化），安全性不损失

**执行顺序（关键）**：

## 五、回测引擎（已实现）

### 5.1 支持 5 种策略类型

| type | 逻辑 | 参数 |
|---|---|---|
| `ma_cross` | 快线上穿慢线持有，下穿空仓 | `fast`, `slow` |
| `boll` | 跌破下轨买入，回中轨卖出（均值回归） | `n`, `k` |
| `boll_break` | 突破上轨买入，跌回中轨卖出（追涨） | `n`, `k` |
| `momentum` | 过去 N 日涨幅 > 阈值则持有 | `lookback`, `threshold` |
| `rsi` | RSI 低于低位买入，高于高位卖出 | `n`, `low`, `high` |

20 个策略卡片复用这 5 种类型，只换参数。

### 5.2 防未来函数（最重要的一行代码）

```python
for i in range(1, n):
    pos = target[i - 1]          # ← T 日仓位由 T-1 日信号决定
    r = bars[i].close / bars[i-1].close - 1
    equity *= (1 + pos * r - cost)
```

信号在 T 日收盘后算出，T+1 日才生效。自测里已经验证：**把最后一天的信号强行改掉，倒数第二个净值点不变**，说明没有信息泄漏。

### 5.3 指标定义

| 指标 | 算法 |
|---|---|
| 总收益 | `equity[-1] - 1` |
| 年化 | `equity[-1] ** (252 / n) - 1` |
| 最大回撤 | 遍历净值，`max((peak - v) / peak)` |
| 夏普 | `mean(日收益) / std(日收益) * sqrt(252)`，无风险利率按 0 |
| 胜率 | 盈利交易数 / 总交易数 |
| 敞口 | 持仓天数 / 总天数（低了说明大部分时间在空仓，别被骗） |
| Calmar | 年化 / 最大回撤 |
| 基准 | 买入持有收益，**必须一起展示**，否则只报绝对收益没有说服力 |

### 5.4 自测结果（真实跑出来的）

随机游走 500 根：

| 策略 | 总收益 | 年化 | 最大回撤 | 夏普 | 胜率 | 交易次数 |
|---|---|---|---|---|---|---|
| ma_cross 5/20 | 3.42% | 1.71% | 32.79% | 0.19 | 46.2% | 13 |
| boll 20/2 | 18.71% | 9.05% | 8.71% | 0.95 | 66.7% | 6 |
| boll_break 20/2 | -30.40% | -16.73% | 40.15% | -0.91 | 37.5% | 16 |
| momentum 20 | -15.99% | -8.43% | 34.97% | -0.33 | 48.4% | 31 |
| 基准（买入持有） | 63.56% | — | — | — | — | — |

这组数据可以**直接拿去当产品卖点**：五个经典策略全部跑输买入持有。这正是"为什么要 AI 帮你诊断"的最好论证。

## 六、假支付方案（三选一，我推荐 B）

| 方案 | 实现 | 演示可信度 | 工时 | 风险 |
|---|---|---|---|---|
| A · 纯 mock | 点「立即支付」直接到账 | 低 | 0.5h | 评委一眼看出是假的，"第一单"加分拿不到 |
| **B · 收款码 + 手动核销** | 显示你个人的收款码 + 订单号后 6 位输入框 | **高** | 2h | 需要你在现场盯着手机确认 |
| C · 微信支付沙箱 | 真实 SDK | 中 | 8h+ | 商户号审核 1-3 天，来不及 |

### 6.1 推荐方案 B 的具体流程

1. 用户点「充 49 元」→ `POST /credits/recharge` 生成 `PENDING` 订单，返回 `order_no` 和你的收款码图片
2. 页面显示：「请扫码支付 ¥49，并在下方输入付款备注里的订单号后 6 位」
3. 用户付完，输入后 6 位 → `POST /credits/confirm`
4. 后端校验：订单 `PENDING` + 后 6 位匹配 → 置 `PAID` → `CreditsService.recharge(points, order_no)`
5. 积分立刻到账，页面余额动画 +1

**为什么这个方案对评分最有利**：钱真的进了你的账户。评委会问"这单是真的吗"，你能掏手机给他看微信收款记录。

### 6.2 关键实现点

```python
# routers/credits.py 片段
@router.post("/confirm")
def confirm_payment(body: ConfirmIn, uid: int = Depends(get_current_user)):
    with engine.begin() as conn:
        order = conn.execute(text(
            "SELECT * FROM recharge_orders WHERE order_no=:no AND user_id=:u"
        ), {"no": body.order_no, "u": uid}).mappings().first()

        if not order:
            raise HTTPException(404, "订单不存在")
        if order["status"] == "PAID":
            # 幂等：重复确认只返回当前余额
            bal = CreditsService.get_balance(conn, uid)
            return {"paid": True, "balance": bal}
        if order["pay_channel"] != "MOCK" and not body.payer_suffix:
            raise HTTPException(400, "请填写付款后 6 位")

        conn.execute(text(
            "UPDATE recharge_orders SET status='PAID', paid_at=NOW(), "
            "pay_trade_no=:suffix WHERE order_no=:no"
        ), {"suffix": body.payer_suffix, "no": body.order_no})

        # 入账走幂等键，重复回调不会重复加
        entry = CreditsService(engine).recharge(
            conn, uid, order["points"], order["order_no"],
            remark=f"充值 {order['price_cny']} 元"
        )
        return {"paid": True, "balance": entry.balance_after}
```

### 6.3 后面接真支付时要改的地方（只有三处）

1. `POST /credits/recharge` 的返回，把 `qr_url` 换成真实 `code_url`
2. 新增 `POST /credits/notify`，接收微信回调，验签后走同一段核销逻辑
3. 删掉 `/credits/mock-pay`

**其余业务代码一行都不用动**，因为入账逻辑已经收口在 `CreditsService.recharge()` 里，幂等键就是 `order_no`。这是当初把账本单独抽出来的回报。
