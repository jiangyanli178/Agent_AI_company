### 3.2 人工闸门：至少两道要真的弹出来

蓝图列了 9 道闸门，其中两道和我们直接相关，而且**必须做进系统，不能停在文档里**：

| 闸门 | 事项 | 我们的实现 |
|---|---|---|
| ⑤ | 价格与条款确认 | 用户点充值时，弹出定价与积分规则确认框 |
| ⑥ | **真实收付款** | 收款核销**必须由你手动点确认**，系统不得自动到账 |

**闸门⑥我们已经天然满足了**——收款码 + 人工核销这个方案，正好就是蓝图要的"资金动作必须老板执行/确认"。
这不算妥协，这是**合规加分项**，演示时要明确说出来：

> 「所有资金动作都必须我本人确认，Agent 只负责准备材料。」

另外两道成本很低的闸门，建议顺手加：

- **闸门④ 对外发布**：AI 生成的获客内容，先进入"待发布"状态，你点一下才发
- **闸门⑦ 投诉退款**：AI 诊断报告如果用户点"不满意"，自动升级给你，不自动回复

### 3.3 一页纸经营周报（阶段 6，唯一必须的财务交付物）

蓝图明确要求。我们的数据库已经能支撑，**就是几条 SQL + 一个模板**：

```sql
-- 本周营收与订单
SELECT COUNT(*) orders, SUM(price_cny) gmv, COUNT(DISTINCT user_id) payers
FROM recharge_orders WHERE status='PAID' AND created_at > DATE_SUB(NOW(), INTERVAL 7 DAY);

-- 积分消耗结构（钱都花在哪个功能上）
SELECT biz_type, COUNT(*) times, SUM(-amount) points
FROM credit_transactions WHERE change_type='CONSUME'
  AND created_at > DATE_SUB(NOW(), INTERVAL 7 DAY)
GROUP BY biz_type ORDER BY points DESC;

-- 真实 token 成本（算毛利用）
SELECT SUM(tokens_in) tin, SUM(tokens_out) tout FROM ai_messages
WHERE created_at > DATE_SUB(NOW(), INTERVAL 7 DAY);

-- Agent 绩效（人事档案）
SELECT * FROM v_agent_kpi;

-- 账目自查（这是一个隐藏加分项）
SELECT (SELECT SUM(balance) FROM credit_accounts) AS balance_sum,
       (SELECT SUM(amount) FROM credit_transactions) AS tx_sum;
```

**最后那条"账目自查"值得单独说**：一个会自己对账的系统，几乎没有队伍会有。

### 3.4 演示必须故意暴露一次失败

蓝图在三处反复强调这一点：

> 演示时插入一次失败重试：故意让测试/合规 Agent 打回一次，展示日志与自动修复。
> **进 → 出 → 中间一次失败重试，比全流程完美更有说服力。**

我们的系统里最容易构造的失败：**让合规 Agent 打回一次 AI 的诊断报告**。

比如 AI 输出里出现"这个策略稳赚"，合规检查拦下 → 打回重写 → 第二次通过 → 日志里留两条记录。
这个既有戏剧效果，又直接证明你有异常处理机制，还顺带展示了合规意识。**一举三得。**

### 官方推荐的演示组合，我们恰好都有

蓝图建议主推 **#1 流水线 + #3 评审循环 + #7 人机闸门**，覆盖"干活、对质量、担责任"三层：

| 官方样例 | 我们对应的东西 |
|---|---|
| #1 串行流水线 | 找策略 → 回测 → 诊断 → 出报告 |

## 六、几条官方红线，别踩

| 红线 | 对我们的含义 |
|---|---|
| **不伪造用户评价** | 演示用的订单、用户、对话必须真实产生。**不要编造"已有 100 个用户"** |
| **密钥不进对话正文** | MiMo API key 只放 `.env`，绝不写进 prompt 或卷宗 |
| **用户数据最小化** | 只收集手机号，不要身份证、不要真实姓名 |
| **资金动作必须老板确认** | 收款核销保持人工，不要图省事改成自动 |
| **对外内容过禁词检查** | AI 生成的文案里"稳赚""保本""必涨"必须被拦下 |

最后一条正好是演示里"故意失败"的素材，**把合规要求变成演示亮点**。
