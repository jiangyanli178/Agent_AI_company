## 一、按量计费（已实现，自测通过）

### 1.1 你的直觉对，但不能完全按 token 实扣

完全按 token 实扣有一个致命的产品问题：**用户在发消息之前不知道自己要花多少，于是不敢提问。**

所以落地成「**预扣封顶 + 按实结算 + 多退不补**」：

```
发消息前   预扣 5 积分（前端显示"本轮最多 5 积分"）
模型返回后 按真实 token 算，比如该扣 2 积分
           退回 3 积分，流水里留一条 REFUND
           前端显示"实扣 2 积分，已退回 3 积分"
```

用户体验是"**比预期便宜**"，这是好体验。反过来"预估 2 实扣 8"会直接流失。

**多退不补**的意思是：如果实际成本超过封顶，我们不多收，自己扛。宁可偶尔少收，也不要让用户觉得被坑。

### 1.2 代码位置与用法

`credits.py` 新增三个方法，复用原有的 consume / refund，**没有引入新表**：

```python
svc.preauth(conn, uid, "AI_CHAT", msg_id)          # 预扣封顶
svc.settle(conn, uid, "AI_CHAT", msg_id, tin, tout) # 按实结算，多退
svc.fail_release(conn, uid, "AI_CHAT", msg_id)      # 调用失败，全额退回
```

幂等键分别是 `pre:{biz}:{id}` 和 `refund:pre:{biz}:{id}`，所以**重复结算不会重复退款**，自测已验证。

### 1.3 参数（拿 MiMo 实价后改这两个数）

| 参数 | 当前值 | 说明 |
|---|---|---|
| `TOKEN_PRICE_IN` | 2.0 | 元/百万输入 token，**待替换** |
| `TOKEN_PRICE_OUT` | 8.0 | 元/百万输出 token，**待替换** |
| `MARKUP` | 12.0 | 成本加价 12 倍 ≈ 毛利 92%，正常一问落在 2 积分 |
| `POINTS_CAP` | 问答 5 / 诊断 60 / 优化 120 | 预扣封顶，也是给用户看的"最多花费" |

自测结果：

| 场景 | 输入 tok | 输出 tok | 应扣积分 |
|---|---|---|---|
| 很短的问题 | 300 | 150 | 1 |
| 正常一问 | 2000 | 1000 | 2 |
| 贴了长文本 | 20000 | 4000 | 5（顶到封顶） |
| 极端超长 | 200000 | 20000 | 5（顶到封顶） |

### 1.4 ⚠️ 一个会让你亏钱的边界

最后一行是坑：用户贴 20 万 token，成本约 0.56 元，但封顶只收 0.5 元，**你是亏的**。

所以**成本失控的真正防线是输入截断，不是封顶**：

```python
MAX_INPUT_TOKENS = {"AI_CHAT": 8000, "DIAGNOSE": 30000, "OPTIMIZE": 80000}
MAX_HISTORY_TURNS = 6     # 只带最近 6 轮上下文
```

**这两条必须在调模型之前执行**，超限就提示用户分段。别指望封顶能兜住成本。

## 二、支付安全：团队没人懂，那就别自己接

### 2.1 先说一个硬门槛，它不是技术问题

**微信支付和支付宝的商户号，都需要企业或个体工商户主体，个人申请不了。**

所以如果你们没有营业执照，"自动到账"这条路**根本不存在**，不是学不会的问题。先去确认有没有主体，再决定要不要花时间。

### 2.2 自己写支付对接为什么必然出事

支付安全真正难的不是"调用付款接口"，而是**回调处理**：

- 微信会重复推通知，你必须幂等（这部分我们的账本已经解决了）
- 任何人都能伪造一个"支付成功"的 POST 打到你的回调地址，**必须验签**
- 验签要用微信平台证书，证书会轮换，要维护证书下载与缓存
- 回调必须 HTTPS，要有域名和证书
- 金额要以回调里的为准，不能信前端传的

这五件事任何一件做错，就是"别人不花钱就能充值"。**没人懂的话，40 小时内不要碰。**

### 2.3 方案 B（收款码 + 人工核销）为什么不是将就，是正确答案

它的安全性来自一个事实：**钱完全不经过你的系统。**

- 没有回调地址 → 没有伪造通知的攻击面
- 没有签名验签 → 没有证书管理的坑
- 不需要 HTTPS 和域名备案就能收付款
- 唯一的漏洞是"用户谎称付了钱骗积分"，而**你低头看一眼手机，就是安全机制**

40 小时内，人工核销不是临时方案，是**唯一合理方案**。

### 2.4 如果确实有主体，想做自动的

只用官方 SDK `wechatpay-python`，不要自己拼签名。但仍然需要：商户号审核（1-3 天）、HTTPS 域名、证书配置。**这套下来 8 小时起步，不建议。**

### 2.5 两个要写进产品的小合规点

1. **积分不可提现、不可转让、不可兑换现金**，写在充值页底部。否则预付式积分会变成类货币，性质完全不同
2. 真支付通道有 **0.6% 手续费**，9.9 元实际到账 9.84 元。算毛利时记得扣掉，虽然比例不大

## 四、24 小时重排（这版的核心是砍）

### 4.1 先砍掉最该砍的：部署 + 每日信号

**整个砍掉，省 6 小时。** 理由是它对你这个项目几乎全是负担：

- 需要定时任务、每日数据更新、日租扣费、暂停恢复，是全项目最重的运维负担
- **回测是即时的，部署是延时的**。现场演示时，部署只能给你看"昨天的信号"，而回测是当场输入当场出图
- 评委看不到"它真的在跑"，只能靠你口头描述

**替代**：把"部署"改成「**加入观察列表**」，每天生成一份信号报告，用静态页面展示预生成的数据。保留这个产品的样子，但不写调度逻辑。

### 4.2 第二个砍法：自由对话 → 单场景诊断

自由对话需要会话管理、流式输出、历史上下文、异常处理。
改成「**策略诊断**」一个固定场景：用户选策略 + 选标的 → 后端自动跑回测 → 把结果喂给 MiMo → 输出诊断报告。

省 1.5 小时，而且**演示效果反而更好**：自由对话的产出是一段文字，诊断的产出是一份可以截图、可以分享、可以收 9.9 元的报告。

### 4.4 如果还是不够，按这个顺序放弃

1. 砍看板（1.5h）—— 答辩时用 SQL 现场查，效果差不多
2. 砍分享页（1h）—— 但获客会弱很多，慎砍
3. AI 诊断降级为"模板生成"（1h）—— 不调模型，用固定话术模板填回测数字，先上线再说
4. 策略库从 9 个砍到 4 个（0.5h）

### 4.5 死也不能放弃

- 回测能当场出图（这是产品的命）
- 充值能收到真钱（这是第一单）
- 积分流水能查（这是闭环的证据）
- 外网链接能打开（这是完成度）
